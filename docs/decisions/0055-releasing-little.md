# 0055 — Releasing little

- Status: accepted
- Date: 2026-10-18

## Context
little is one binary, with its built-in theme compiled in, but nobody can
download it: each install builds it from source, with Rust 1.96 or later,
in a few minutes, and the workflow the manual gives for GitHub Pages builds
it again on each run. little's plugins are released from tags that name
them, by a workflow of little's own
([0052](./0052-releasing-plugins-from-tags.md)), with their third-party
notices ([0054](./0054-third-party-notices.md)), which leaves little's own
tags to be like `v0.1.0`. The repository's releases are immutable, so a
published release's files can't be changed, nor its tag moved.

Some of the crates little uses compile C code: onig_sys, Oniguruma, which
highlights code, and aws-lc-sys and ring, for HTTPS. A Linux binary built
against glibc runs only where that version of glibc, or a later one, is;
one built statically, against musl, runs on any distribution, but musl's
allocator is slow when threads allocate at once. Pagefind's own binary
uses jemalloc there, for that reason, and its crate brings jemalloc into
little's builds for musl, unused.

`little` is another crate's name on crates.io.

## Options considered
- **Tools:**
  - [dist](https://github.com/axodotdev/cargo-dist), which writes a
    release workflow from its config, with installer scripts and
    checksums. Its workflow is generated, and regenerated by each new
    version of dist, so it's changed through dist's settings, not by hand,
    and releases in dist's own way, unlike the plugins' workflow, which is
    little's.
  - [cargo-zigbuild](https://github.com/rust-cross/cargo-zigbuild), or
    cross, which cross-compile every target from one runner, with Zig, or
    Docker.
  - A workflow of little's own, as the plugins have, that builds each
    target on a GitHub runner of its own system, which GitHub has for
    Linux, macOS, and Windows, on x64 and arm64, with Rust's own
    toolchains, and each system's C compiler.
- **Targets:**
  - Linux's: against glibc, built on Ubuntu 24.04, so needing glibc 2.39
    or later; or against musl, statically, with musl-tools' compiler for
    their C code, and musl's allocator, or jemalloc, as Pagefind's binary
    uses.
  - macOS's: one for Apple silicon and one for Intel; or a universal
    binary of both, twice the size.
  - Windows': linked to the Visual C++ runtime, which not every Windows
    has; or with it built in, with `crt-static`.
- **Archives:**
  - with the version in their names, as ripgrep's are; or without it, as
    Ruff's and uv's are, so GitHub's `releases/latest/download/` URL
    always leads to the latest, for a link or a script that never changes;
  - with their files in a folder, as ripgrep's and Ruff's are; or at their
    root, as mdBook's and Zola's are, so `tar -xz little` takes the binary
    alone.
- **crates.io:**
  - not published, so `cargo install` builds little from git;
  - published, under another name, like `little-docs`, with the command
    still `little`, so `cargo install` finds it, as does
    [cargo-binstall](https://github.com/cargo-bins/cargo-binstall), which
    downloads a binary from the URL in a crate's metadata, else builds it;
  - with an API token, kept in a secret; or with crates.io's trusted
    publishing, which gives a workflow a token for one run, but can't
    publish a crate's first version.
- **Signing:** Apple's notarization, with a Developer ID, which costs $99 a
  year, and a code signing certificate for Windows, so macOS and Windows
  don't stop a binary downloaded with a browser; or none yet, with
  checksums, and GitHub's attestations, which say where each archive was
  built.
- **The Pages workflow:** it downloads the latest release, from a URL that
  never changes, so a release that breaks a site breaks its next build, or
  a version named in its URL, which a site changes when it's ready.

## Decision
- little is released from a tag of its version, `v<version>`, like
  `v0.1.0`, on a commit on `main`, pushed by hand, which runs
  `.github/workflows/release.yml`. As a plugin's does, it first checks that
  the tag is a version, `X.Y.Z`, with no pre-release; that its commit is on
  `main`; that the version has no release, not even a draft; and that it's
  the version in `Cargo.toml`.
- It builds little for six targets, each on a GitHub runner of its system,
  with `--locked`, and checks each binary runs, by building a site with a
  code block to highlight:
  - `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`, static,
    with their C code compiled by musl-tools' `musl-gcc`, and jemalloc as
    their allocator, with 64 KiB pages on arm64, as Ruff and uv build it,
    so it runs on kernels with 4, 16, or 64 KiB pages;
  - `x86_64-apple-darwin` and `aarch64-apple-darwin`;
  - `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc`, with the C
    runtime built in.
- Each binary is packed at the root of an archive, `little-<target>.tar.gz`,
  or `.zip` for Windows, with no version in its name, with `LICENSE` and the
  third-party notices 0054 sets. A `SHA256SUMS` lists each archive's
  checksum, and GitHub attests where each was built, for
  `gh attestation verify`.
- The release, titled like `little 0.1.0`, is the repository's latest,
  which a plugin's never is. gh uploads its files to a draft, and publishes
  it once they're there, so a run that fails publishes nothing. Its notes
  say how to install it, link to the manual's install page, on GitHub, at
  the tag, and
  list what's changed since little's last tag, with git-cliff and the
  plugins' `cliff.toml`: the commits that changed what's built into little,
  `src/`, `theme/`, `wit/`, `Cargo.toml`, or `Cargo.lock`, not the
  manual's, nor the plugins'. A first release says it's the first.
- little's crate is `little-docs`, and its binary still `little`. It
  includes only what little is built from, `src/`, `theme/`, and `wit/`,
  with the example that writes its notices, in `examples/`, `LICENSE`, and
  `README.md`, and CI packages it for each
  pull request, with `cargo package --locked`, so a file it needs that's
  left out fails there. Its metadata leads cargo-binstall to the release's
  archive for its target, and never to a third party's build of it.
- The workflow publishes the crate once the release is out, as
  cargo-binstall downloads its archives, in a job of its own, in an
  environment, `crates-io`, with a token from crates.io's trusted
  publishing. Its first version is published by hand, as trusted
  publishing can't, so until the crate is on crates.io, and once it has the
  version, the job says so, and skips it, so it can be run again.
- A pull request that changes `release.yml`, `Cargo.toml`, or `Cargo.lock`
  runs the workflow, but for its release and crates.io jobs, which alone
  can write, so a change that would break a release fails there.
- The binaries aren't signed yet. The manual's install page says how to run
  one that macOS or Windows stops, and how to check one, by its checksum or
  its attestation.
- The manual's workflow for GitHub Pages downloads little, by its version,
  for Linux on x64, rather than build it. A release's pull request,
  `chore: release <version>`, raises that version, with `Cargo.toml`'s and
  `Cargo.lock`'s.
- [`RELEASING.md`](https://github.com/withlittle/little/blob/main/RELEASING.md)
  lists the steps.

## Consequences
- little can be installed without Rust: downloaded, by a script, from a URL
  that never changes, or with cargo-binstall, and a site's workflow
  downloads it in seconds, rather than build it in minutes.
- `cargo install` installs `little-docs`, from crates.io, git, or a clone;
  the command it installs is the same.
- Linux's binaries run on any distribution, but their C code is built
  against musl, not the system's C library, with jemalloc, more C, in place
  of musl's allocator.
- Each release runs six builds, of up to some ten minutes, on GitHub's
  runners, which are free for a public repository.
- A version on crates.io, like a release, is never changed, but can be
  yanked; the crate is published last, so a run that fails before the
  release publishes neither.
- Limits, for now:
  - the binaries aren't signed, so macOS and Windows may stop one
    downloaded with a browser;
  - there's no installer script, Homebrew formula, or Linux package;
  - Linux on 32-bit systems, or on other architectures, like RISC-V,
    isn't built for;
  - the workflow doesn't run the tests, which CI ran on `main`, but checks
    that each binary runs;
  - pre-releases, like `v0.2.0-rc.1`, aren't supported;
  - the crate's first version, and its trusted publisher, are set up by
    hand.
